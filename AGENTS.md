# AGENTS.md — правила работы AI с Nastya Story

Этот файл обязателен к чтению перед изменениями в репозитории.

## 1. Источник истины

Репозиторий является канонической памятью проекта. Не считать историю чата, собственную память модели или предположения каноном, если информация не зафиксирована в репозитории.

## 2. Определить роль

### Если ты ChatGPT в режиме проектирования
Рабочая зона: `docs/`.
Можно создавать и корректировать спецификации, базу мира, контент, графы и задания после обсуждения с владельцем. По умолчанию не изменять `game/`.

### Если ты Codex в режиме разработки
Основная рабочая зона: игровой код и технические файлы реализации. Проектные документы из `docs/` являются требованиями. Не менять дизайн для удобства реализации без согласования.

## 3. Правила Codex

1. Перед реализацией прочитать `README.md`, этот файл и `docs/MASTER_SPEC.md`.
2. Если владелец указал конкретный TASK — работать по нему.
3. Если сказано «возьми следующее готовое задание», брать только из `docs/tasks/ready/`.
4. Прочитать ссылки `related_specs`, `related_entities`, `dependencies` внутри TASK.
5. Проверить существующую реализацию перед изменениями.
6. Не вводить новые игровые механики, сюжетные факты, персонажей, характеристики или баланс без требования.
7. Если обнаружено существенное противоречие требований — не угадывать; описать блокер владельцу.
8. После начала работы задача должна находиться в `in_progress`.
9. После реализации подготовить implementation report по шаблону `docs/templates/IMPLEMENTATION_REPORT_TEMPLATE.md` и перевести материалы в `review`.
10. В `done` переводит только владелец либо AI после явного подтверждения владельца о приёмке.

## 4. Что Codex не должен читать без необходимости

Не требуется рекурсивно читать весь `docs/`. Использовать TASK как карту контекста и загружать связанные документы. Это уменьшает шум и риск использования устаревшего/несвязанного материала.

## 5. Изменение документации при реализации

Codex может:
- исправить очевидную техническую ссылку/опечатку, если смысл не меняется;
- дополнить implementation report;
- предложить изменение спецификации.

Codex не должен самостоятельно менять каноническую игровую логику в `docs/systems/`, `docs/world/` или `docs/content/`, если это не является явной частью TASK.

## 6. Отчётность

Implementation report должен содержать минимум:
- статус;
- выполненные требования;
- изменённые файлы;
- тесты/проверки;
- отклонения от TASK;
- незавершённые пункты;
- известные проблемы;
- commit SHA, если доступен.

## 7. Никаких скрытых решений

Любое решение, которое влияет на последующее проектирование (новое состояние, ID, формат данных, ограничение архитектуры), должно быть явно отражено в отчёте и при необходимости вынесено владельцу для фиксации в канонической документации.
