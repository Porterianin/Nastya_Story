# AGENTS.md — правила работы AI с Nastya Story

Этот файл обязателен к чтению перед изменениями в репозитории.

## 1. Источник истины

Репозиторий является канонической памятью проекта. Не считать историю чата, собственную память модели или предположения каноном, если информация не зафиксирована в репозитории.

## 2. Определить роль

### Если ты ChatGPT в режиме проектирования
Рабочая зона: `docs/`.
Можно создавать и корректировать спецификации, базу мира, контент, графы и задания после обсуждения с владельцем. По умолчанию не изменять `game/`.

### Если ты Codex в режиме разработки
Основная рабочая зона: игровой код и технические файлы реализации. Проектные документы из `docs/` являются требованиями. Не менять дизайн для удобства реализации без согласования.

## 3. Обязательное чтение перед изменениями

Перед проектной или технической работой прочитать:

1. `README.md`;
2. этот файл;
3. `docs/MASTER_SPEC.md`;
4. `docs/REPOSITORY_MAP.md` — практическую карту файлов и зависимостей.

После этого читать только документы, относящиеся к текущей задаче.

## 4. Правила Codex

1. Если владелец указал конкретный TASK — работать по нему.
2. Если сказано «возьми следующее готовое задание», брать только из `docs/tasks/ready/`.
3. Прочитать ссылки `related_specs`, `related_entities`, `dependencies` внутри TASK.
4. Проверить существующую реализацию перед изменениями.
5. Не вводить новые игровые механики, сюжетные факты, персонажей, характеристики или баланс без требования.
6. Если обнаружено существенное противоречие требований — не угадывать; описать блокер владельцу.
7. После начала работы задача должна находиться в `in_progress`.
8. После реализации подготовить implementation report по шаблону `docs/templates/IMPLEMENTATION_REPORT_TEMPLATE.md` и перевести материалы в `review`.
9. В `done` переводит только владелец либо AI после явного подтверждения владельца о приёмке.

## 5. Синхронность изменений документации

Любая каноническая правка должна сопровождаться проверкой всех файлов, где тот же факт или правило отображается или используется.

Нельзя считать изменение завершённым после правки одного файла, если оно затрагивает связанные представления.

Перед commit обязательно выполнить Change Impact Check по `docs/REPOSITORY_MAP.md` и `docs/MASTER_SPEC.md`.

Особенно проверять:

- карточку сущности и её родительскую сущность;
- world graph;
- navigation graph;
- связанные NPC/character canon;
- действия, эффекты и квесты;
- сцены и диалоги;
- UI/HUD, если факт виден игроку;
- существующие TASK, если они могли зафиксировать старую версию требования.

Если связанные файлы неизвестны, сначала найти их. Не оставлять известную несинхронизированную правку «на потом».

## 6. Что Codex не должен читать без необходимости

Не требуется рекурсивно читать весь `docs/`. Использовать TASK и `docs/REPOSITORY_MAP.md` как карту контекста и загружать связанные документы. Это уменьшает шум и риск использования устаревшего/несвязанного материала.

## 7. Изменение документации при реализации

Codex может:
- исправить очевидную техническую ссылку/опечатку, если смысл не меняется;
- дополнить implementation report;
- предложить изменение спецификации.

Codex не должен самостоятельно менять каноническую игровую логику в `docs/systems/`, `docs/world/` или `docs/content/`, если это не является явной частью TASK.

Если реализация требует изменения канонической документации, это должно быть явно предусмотрено TASK или согласовано с владельцем.

## 8. Отчётность

Implementation report должен содержать минимум:
- статус;
- выполненные требования;
- изменённые файлы;
- тесты/проверки;
- отклонения от TASK;
- незавершённые пункты;
- известные проблемы;
- commit SHA, если доступен.

## 9. Никаких скрытых решений

Любое решение, которое влияет на последующее проектирование (новое состояние, ID, формат данных, ограничение архитектуры), должно быть явно отражено в отчёте и при необходимости вынесено владельцу для фиксации в канонической документации.
